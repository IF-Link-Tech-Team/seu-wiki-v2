# 公众号采集接入

公众号和官网共用 `sources → articles → analyses → publications`，以及既有的事件归组和公开读取层。不新增图片表。

## 数据与图片

- 极致了列表使用 `history_by_ghid`；账号可配置 `ghid`、`wxid`、已知文章 `url` 或 `nickname`，返回名称必须与配置的 `nickname` 一致。
- 详情使用 GET `article_detail` 的 `mode=2`，分别读取纯文本 `content` 和 HTML `content_multi_text`。
- HTML 经现有清洗逻辑进入 `articles.body_html`；封面及正文图片链接去重后进入 `articles.media`。
- 图片沿用官网签名代理和 `AIHOT_DATA_DIR/imgcache` 缓存，不作永久原图归档，不做 OCR。
- 平台身份、封面、响应版本和请求回执 ID 保存到 `articles.raw.dajiala`；完整响应先保存到 `receipts`。
- 仅补充 HTML 或图片时，不增加文本修订、不重新付费分析，刷新现有公开投影。

## 付费与判重

请求仍受现有预算与回执保护。接口版本和详情模式包含在请求身份中，避免错误复用旧模式的结果。同一长链接去除跟踪参数后复用文章；已取得详情的文章不重复购买。结果不明的请求保留回执，先核对后处理。

这里只接通现有身份判重和事件归组。跨渠道正文相似判重仍待另行设计。

## 服务器每日运行

生产沿用既有 worker，无需另起本地 watcher 或系统 cron。`COLLECT_ENABLED=true` 时，`cron.sources.mp-reconcile` 每 15 分钟检查哪些公众号到期；每个已确认公众号的 `interval_minutes=1440`，因此每 24 小时至多自动尝试一次。首次执行前原子领取执行权，失败或预算不足也记录当天尝试；旧队列重试、并发任务不会再次查询。源仍有 pending/unknown 付费回执时停止自动请求，沿用原有恢复与人工核对机制。

官网仍由 `sources.schedule` 按各自间隔采集；公众号不参与官网的动态间隔调整。采集后复用同一正文、模型分析、发布和事件归组任务。

部署检查：

1. PR 的 `check`、`docker` 检查通过，合并后完成主分支检查和 `seuwiki-prod` 环境审批，再确认 Deploy 成功。
2. 将 `DAJIALA_KEY` 安全写入服务器项目的 `.env`；不提交仓库、不输出密钥。检查 worker 读取到凭据，生产开发登录开关仍关闭。
3. `scripts/seed.ts` 只新增源，不覆盖后台修改。因此需备份受影响源配置，显式同步清单中 84 个公众号的定位、启用和 1440 分钟间隔；仅更新本轮修复的 25 个官网源的 `config`，保留官网启停、频率和全文权限。不对全部数据库执行无条件覆盖。
4. 极致了预算保持有界。本次生产限额为每分钟 120 次、每小时 1000 次、滚动 24 小时 1000 次；这是请求次数上限，实际扣费以回执为准。84 个账号只查询列表，按首轮实际单价 0.14 元约 11.76 元/轮；新增文章详情和模型费用另计。
5. 核验公众号源数与间隔、调度表、抓取回执、文章入库、分析与公开投影；检查正式站页面、CSS/JS、图片及原文跳转。HTTP 200 或构建成功不能代替这些检查。

停用公众号时只禁用对应 `mp_account` 源，不关闭整个采集 worker。发生额度耗尽或供应商失败时保留回执，后台查看失败原因；不要通过重启或修改时间窗口重复收费。生产源默认摘要和原文链接，只有获得来源许可后才启用全文展示。
